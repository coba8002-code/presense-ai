# PetSense AI Constitution

## Core Principles

### I. 개 전용 MVP와 확인 가능한 설명

- 현재 제품은 개만 지원한다. 고양이 학습과 실시간 음성 요청은 거부한다.
- 영상에서 개가 아닌 동물이나 알 수 없는 대상을 보면 판단을 보류한다.
- 직접 관찰한 행동, 보호자의 기록, 행동 가설, 확인된 후속 결과를 구분한다.
- 동물 언어 번역, 의도 분석 정확도, 질병 진단을 검증된 기능처럼 말하지 않는다.
- 긴급한 건강 징후에는 수의사의 도움을 안내한다.

### II. 출처와 사용권을 먼저 확인

- 데이터마다 출처, 버전, 사용권, 동의, 검토 기록과 근거를 남긴다.
- 사용권이 확인되지 않은 데이터는 학습에 사용하지 않는다.
- TV와 YouTube 자료는 필요한 권리와 플랫폼 허가 없이 내려받거나 학습하지 않는다.
- 기존 데이터 검토 기록을 보존한다. 소유자의 진술과 독립적으로 검증한 근거를 구분한다.

### III. 실제 결과로 검증

- 학습·검증·시험 데이터에 같은 개가 섞이지 않게 나눈다.
- 실제 모델 평가에는 정확도, macro F1, 혼동 행렬, 보정과 판단 보류 지표를 기록한다.
- 측정값과 재현 가능한 실행 기록이 없으면 학습이나 정확도가 검증됐다고 말하지 않는다.
- 인공 데이터 실행은 기술 점검으로만 기록하고 실제 행동 분석 성능으로 쓰지 않는다.
- 변경한 동작에 맞는 검사를 실행하고, 실패·제약·미완료 항목을 그대로 보고한다.

### IV. 개인정보와 승인 범위 준수

- API 키, 개인정보, 비공개 녹음과 영상을 소스나 Git 기록에 넣지 않는다.
- 미디어 수집과 외부 전송에는 동의와 접근 권한을 확인한다.
- 사용자 승인 없이 유료 API를 호출하거나 운영 환경에 배포하지 않는다.
- 커밋, 푸시, PR 생성은 사용자가 명시적으로 요청했을 때만 한다.
- PR 병합 전에는 CI가 통과해야 한다.

### V. 필요한 범위만 변경

- 요청과 관계없는 파일과 동작은 수정하지 않는다.
- 기존 소스를 먼저 읽고 작은 단위로 작업한다. 더 나은 별도 방법은 제안만 한다.
- 사용자에게 한국어로 짧고 쉽게 설명한다.
- C# 파일은 UTF-8 BOM 없음과 CRLF를 사용하고 ref·out 매개변수 메서드는 만들지 않는다.

## 기술과 작업 범위

- 백엔드는 Python 3.12와 FastAPI, 음성 학습은 Python/PyTorch를 기준으로 한다.
- Flutter Android/iOS 앱과 클라우드 VLM은 목표 구조다. 구현·배포 여부는 실제 코드로 확인한다.
- 한국어와 영어 기반을 먼저 만들고, 전 세계 출시나 전체 번역 지원을 완료했다고 단정하지 않는다.
- README.md, AGENTS.md, CONSTRAINTS.md와 현재 작업 문서를 먼저 읽는다.
- Issue #1의 초기 계획보다 현재 사용자 지시와 개 전용 MVP 범위를 우선한다.
- 이전 통합 ZIP의 내용은 직접 확인하기 전까지 가져왔다고 말하지 않는다.

## 개발 순서와 확인

1. `$speckit-specify`로 기능 요구와 완료 조건을 작성한다.
2. 필요하면 `$speckit-clarify`로 모호한 조건을 정리한다.
3. `$speckit-plan`으로 구현 방법과 위 원칙의 충족 여부를 확인한다.
4. `$speckit-tasks`로 확인 가능한 작은 작업을 만든다.
5. `$speckit-analyze`로 요구·계획·작업이 서로 맞는지 확인한다.
6. `$speckit-implement`로 승인된 범위의 구현과 검사를 진행한다.

애플리케이션 검사는 Linux 또는 WSL의 Python 3.12 환경에서
`python -m unittest discover -s tests -v`로 실행한다. 테스트에서 네트워크를 사용하지 않는다.
Spec Kit 도구는 Python 스크립트를 사용하며 Windows와 WSL에서 실행한다.

## Governance

이 문서는 기존 프로젝트 규칙을 Spec Kit에 연결한다. 사용자 지시와 AGENTS.md를 우선한다.
계획 단계와 구현 후 검토에서 원칙 위반 여부를 확인하고 예외가 있으면 이유를 기록한다.
규칙 변경은 사용자 지시 또는 확인된 프로젝트 근거에 따라 이 문서에 반영한다.
호환되지 않는 원칙 변경은 major, 원칙 추가는 minor, 설명 수정은 patch 버전을 올린다.
